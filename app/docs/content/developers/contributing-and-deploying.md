## Contributing

Issues and pull requests are welcome in both repositories:

- Engine: [invarislabs/invaris-agentsec](https://github.com/invarislabs/invaris-agentsec) (see its
  [CONTRIBUTING.md](https://github.com/invarislabs/invaris-agentsec/blob/main/CONTRIBUTING.md))
- Dashboard and these docs: [invarislabs/invaris-agentsec-dashboard](https://github.com/invarislabs/invaris-agentsec-dashboard)

A typical change:

1. Create a branch from `main`.
2. Make the change with tests (and docs, under `app/docs/content/`, if behaviour or UI changed).
3. Run the tests: `pytest` (and with `TEST_DATABASE_URL` for database changes).
4. Open a pull request. CI runs the tests on Postgres and SQLite.

**CLA.** On your first pull request, the CLA Assistant bot asks you to confirm the
[Contributor License Agreement](https://github.com/invarislabs/invaris-agentsec-dashboard/blob/main/CLA.md) by replying
with the comment it quotes. You do this once; contributions are licensed under the Apache License 2.0.

**Security problems** must be reported privately as described in the engine's
[SECURITY.md](https://github.com/invarislabs/invaris-agentsec/blob/main/SECURITY.md), not in a public issue.

## Deploying the dashboard

The `Dockerfile` builds one image that applies migrations (`alembic upgrade head`) and serves on `$PORT` (default
8000) behind a TLS-terminating proxy. It runs on any container host with Postgres. It needs `DATABASE_URL`,
`SECRET_KEY`, `PUBLIC_URL`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`, a daily prune, and nothing else.

```bash
docker build -t agentsec-dashboard .
docker run -p 8000:8000 --env-file .env agentsec-dashboard
```

Install a different engine build with `--build-arg AGENTSEC_REQUIREMENT="..."`.

### Free deployment: Render and Neon

The repository is set up to run at no cost:

| Piece | Service | Notes |
|---|---|---|
| Web app | Render free web service (`render.yaml`) | 512 MB, 0.1 CPU; sleeps after 15 minutes idle and takes about a minute to wake |
| Database | Neon Free plan | Sleeps after 5 minutes idle, wakes in under a second |
| Daily clean-up | GitHub Actions (`.github/workflows/prune.yml`) | Free for public repositories |

1. **Neon.** Create a project (pick a region next to your Render region; `render.yaml` uses Singapore). Set the
   autoscaling maximum to 0.25 CU. Copy two connection strings: with connection pooling on (host contains
   `-pooler`) for `DATABASE_URL`, and with it off for `DATABASE_DIRECT_URL`.
2. **Render.** New > Blueprint, pick the repository. It creates one free web service and asks for the values marked
   `sync: false`: the two Neon URLs, `PUBLIC_URL` (`https://<service>.onrender.com`), and the GitHub OAuth values (type
   `pending` for now). `SECRET_KEY` is generated by Render. When live, `/healthz` answers `{"ok":true}`.
3. **GitHub sign-in.** Create an OAuth app with homepage `https://<service>.onrender.com` and callback
   `https://<service>.onrender.com/auth/github/callback`. Set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` in Render;
   it redeploys.
4. **Daily clean-up.** Add a repository secret `PRUNE_DATABASE_URL` with the Neon **direct** URL and run the **prune**
   workflow once to check it.
5. **Send reports** with `agentsec upload --server https://<service>.onrender.com` or the action's `dashboard-url`.
   Wake the service first in CI: `curl -fsS --retry 8 --retry-delay 10 --retry-all-errors https://<service>.onrender.com/healthz`.

To stay at $0: do not add a payment method to Render, do not change the plan in `render.yaml`, keep Neon on the
Free plan. Render's own free Postgres is not used because it is deleted 30 days after creation.

### Daily clean-up {#daily-clean-up}

`python -m app.maintenance prune` deletes runs older than each owner's plan retention. Schedule it daily with the
production database URL (the included workflow runs at 03:17 UTC). GitHub disables scheduled workflows after 60 days
without repository activity; re-enable them from the Actions tab if that happens.

### Updates

Render deploys `main` after CI passes (`autoDeployTrigger: checksPass`), and migrations run on start. Secrets live
only in Render, Neon and GitHub Actions secrets; none is in the repository. Upgrading an existing deployment to
migration `0002` adds `reports.inconclusive` and fills it for stored runs.

### The documentation ships with the app

`/docs` is part of the same service and deployment: no separate build, host or domain. Every deploy serves the docs
from the same commit as the code they describe. A malformed page fails `tests/test_docs.py` in CI, so it should never
be deployed; if one is, the dashboard still starts and serves every other page, leaves the bad one out (it answers
404) and logs `documentation page skipped: <file>: <reason>` from the `app.docs` logger.
